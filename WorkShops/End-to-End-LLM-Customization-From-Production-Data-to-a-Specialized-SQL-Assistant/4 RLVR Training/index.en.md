# Lab 3: Reinforcement Learning from Verifiable Rewards (RLVR)

## What you will learn

- How GRPO (Group Relative Policy Optimization) learns from execution feedback
- Why SFT before RLVR is critical (demonstrated via ablation study)
- How to configure RLVR hyperparameters for a small SQL dataset
- How to run training jobs in parallel and monitor their progress

---

## Get started

1. In the JupyterLab file browser, open **`03-rlvr-training.ipynb`**.

2. Run all cells in order. The notebook is divided into four parts:

### Part 1: Configure Both Trainers (~2 minutes)

Two RLVR trainers are configured against the same data and the same reward function:
- **`sft_rlvr_trainer`**: Starts from the SFT model (Lab 2 output), `rollout_n = 32`
- **`base_rlvr_trainer`**: Starts from the base Llama 3.2 3B (ablation), `rollout_n = 8`

Every other hyperparameter is identical. `rollout_n` differs deliberately: generation dominates RLVR wall-clock, so running the ablation arm at 32 rollouts would roughly quadruple its generation work and push the lab past its time slot.

Because `rollout_n` is the GRPO group size, the smaller group also makes the ablation arm's advantage estimates noisier. The notebook discusses what that does and does not let you conclude — in short, the *direction* of the result is solid, but do not compare curve smoothness between the two arms.

### Part 2: Launch Training (~1 minute)

Both jobs are launched simultaneously with `wait=False`. This runs them in parallel, cutting wall-clock time from ~2 hours to ~1 hour.

### Part 3: Monitor (~60 minutes)

The monitor cell polls both jobs every 60 seconds and displays their status:
```
============================================================
  RLVR TRAINING MONITOR
============================================================
  SFT + RLVR:   InProgress   Training
  Base + RLVR:  InProgress   Training

  Last checked: 14:32:15
```

The cell blocks until both jobs reach a terminal state. You can also monitor in the AWS Console under **SageMaker > Training > Training Jobs**.

### Part 4: Evaluate (~30 minutes)

After training completes, four evaluations run — each model against the validation and combined sets.

Only **two evaluation jobs can run at once**, so the notebook runs them in two batches of two:

1. **Batch 1** — SFT+RLVR (validation + combined), then a cell blocks until both finish.
2. **Batch 2** — Base+RLVR (validation + combined), then a cell blocks until both finish.

Run the cells in order and do not skip the waiting cell between the batches. Launching all four at once exceeds the concurrency limit and the extra jobs will fail to start.

Each evaluation scores only its own fine-tuned model. The base Llama 3.2 3B was already scored on both datasets in Lab 2, and Lab 4 pulls that result into the final comparison — so re-running it here would only duplicate a row.

## Key hyperparameters

| Parameter | Value | Why |
|-----------|-------|-----|
| `rollout_n` | 32 | 32 SQL attempts per prompt, compared against each other (the ablation arm uses 8 — see below) |
| `learning_rate` | 1e-6 | 10x lower than SFT — RL updates are noisy |
| `kl_loss_coef` | 0.04 | Prevents divergence from the SFT checkpoint |
| `max_epochs` | 60 | ~60 gradient steps (1 step/epoch at batch=128) |
| `rollout_temperature` | 0.8 | Diverse but not random exploration |

## What to expect

After both jobs complete, review the "Expected Results" markdown in the notebook and compare the training curves in MLflow. The expected finding:

| Approach | Final Reward (approximate) |
|----------|---------------------------|
| SFT + RLVR | **~0.55** |
| Base + RLVR | ~0.49 |

SFT+RLVR should win because SFT provides a warm start (the model can already generate valid SQL) and formatting discipline (concise responses without markdown wrapping).

### Why your numbers will be different

Your run will not reproduce these values exactly, and that is expected. RLVR is stochastic in several places at once:

- **Rollout sampling** — each prompt is answered `rollout_n` times at `rollout_temperature = 0.8`, so different samples earn different rewards and produce different gradients.
- **Relative advantages** — GRPO computes advantage *within* each group of rollouts, so a lucky or unlucky batch shifts that step's update.
- **All-or-nothing reward** — the evaluator executes the generated SQL, so reward moves in coarse jumps rather than smoothly.
- **Your own dataset** — the queries come from `pg_stat_statements` on your Aurora cluster and the descriptions were generated by Bedrock, so the training data itself differs.
- **Only 60 steps** — the run has not fully converged, so where the curve lands is somewhat arbitrary.

Expect final rewards within roughly ±0.05 of the values above, with bumpy rather than monotonic curves. A step where reward drops is normal.

Judge the lab by whether the *comparison* holds — SFT+RLVR starting higher, finishing higher, and training more stably (smoother entropy decline, steadier episode length, advantage settling toward 0 sooner) — not by matching exact numbers. If the base model appears to match or beat SFT+RLVR, that is far more likely to be sampling noise on a short run than a real reversal.

## MLflow experiments created

| Experiment | Content |
|-----------|---------|
| `rlvr-training` | SFT+RLVR training metrics (reward, entropy, gradient norm) |
| `rlvr-base-training` | Base+RLVR training metrics |
| `rlvr-eval-validation` | SFT+RLVR evaluation scores |
| `rlvr-eval-combined` | SFT+RLVR evaluation on production set |
| `rlvr-ablation-eval-validation` | Ablation evaluation scores |
| `rlvr-ablation-eval-combined` | Ablation evaluation on production set |

The two training experiments are where the ablation actually lives — the evaluation scores tell you which model won, but only the reward curves show you why. The notebook prints a direct MLflow link after training completes, and the **Reviewing Results** module at the end of the workshop covers how to read these curves in detail.
