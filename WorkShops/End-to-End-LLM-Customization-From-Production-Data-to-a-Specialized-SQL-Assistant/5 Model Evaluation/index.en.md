## Get started

1. In the JupyterLab file browser, open **`04-model-evaluation.ipynb`**.

2. Run all cells in order. The notebook is divided into three parts:

### Part 1: Benchmark Frontier Models (~15 minutes)

The notebook calls Claude Haiku 4.5 and Claude Sonnet 4.6 via Amazon Bedrock with the same prompt and schema the fine-tuned models were trained on. Each model generates SQL for every sample in both the validation and combined datasets.

The `workshop_evaluator` Lambda you deployed in **Lab 2, Part 1** scores the outputs — the same scorer used for the fine-tuned models, which is what makes this an apples-to-apples comparison. (If a later cell fails reporting that the function is missing, Lab 2 did not complete — run it first.)

**What success looks like.** The cell prints its progress per model and dataset, then a completion line:

```
Evaluating: Claude Haiku 4.5
  Generating completions for Claude Haiku 4.5 (37 samples)...
    10/37 complete
    ...
  Scoring validation (37 samples)...
    reward=0.380, exec=0.98, f1=0.12
  Generating completions for Claude Haiku 4.5 (241 samples)...
  Scoring combined (241 samples)...
    reward=0.41, exec=0.98, f1=0.15
Evaluating: Claude Sonnet 4.6
  ...

Benchmark complete!
```

Sample counts match your dataset; the exact scores will differ. The signal that Part 1 succeeded is the final `Benchmark complete!` after both models have a `reward=...` line for each dataset. If a model fails mid-run, individual samples log a failure but the batch continues — a handful of failures is fine; a `reward` of 0.00 across a whole batch means every call failed (usually Bedrock access — re-check the Lab 0 verification).

### Part 2: Log to MLflow (~1 minute)

Results are logged to dedicated experiments (`sota-eval-validation`, `sota-eval-combined`) so they appear alongside the fine-tuned model results.

**What success looks like.** One `Logged:` line per model per experiment:

```
Logged: claude-haiku-4-5-baseline -> sota-eval-validation
Logged: claude-sonnet-4-6-baseline -> sota-eval-validation
Logged: claude-haiku-4-5-baseline -> sota-eval-combined
Logged: claude-sonnet-4-6-baseline -> sota-eval-combined
```

Four lines means both models were logged to both experiments. If you see fewer, a model's results were missing from Part 1 — re-run it before the unified comparison, or its row will be blank in the tables below.

### Part 3: Unified Comparison (~1 minute)

The final cells pull results from all evaluation experiments across the workshop and display two ranked tables:

**Validation set** — unseen queries the model never saw during training.

**Combined set** — reflects real production query distribution (90% of traffic).

## What to expect

Your validation table should look roughly like this. Treat these as reference values, not targets to match:

```
                           Exec Success  Exact Match  Result F1  Reward Score
Model
Llama 3.2 3B (SFT + RLVR)        ~1.00        ~0.38      ~0.42         ~0.59
Llama 3.2 3B (SFT)               ~0.99        ~0.37      ~0.41         ~0.58
Llama 3.2 3B (RLVR only)         ~0.99        ~0.22      ~0.25         ~0.47
Llama 3.2 3B (base)              ~0.96        ~0.19      ~0.20         ~0.43
Claude Haiku 4.5                 ~0.98        ~0.10      ~0.12         ~0.38
Claude Sonnet 4.6                ~0.94        ~0.11      ~0.12         ~0.37
```

### Why your numbers will be different

Your run will not reproduce these values exactly, and that is expected:

- **Upstream training variance** — these scores evaluate the checkpoints you produced in Labs 2 and 3. RLVR in particular is stochastic (sampled rollouts, group-relative advantages, all-or-nothing execution rewards), so the model being scored here is not bit-identical to the one that produced the table above.
- **Your own dataset** — the queries come from `pg_stat_statements` on your Aurora cluster and the descriptions were generated by Bedrock, so both the training data and the validation split differ from run to run.
- **A small validation split** — with only ~37 held-out samples, a single query flipping from wrong to right moves Exact Match by roughly 0.03. Expect the fine-tuned rows to jump around more than the ranking does.
- **Frontier model sampling** — Claude Haiku and Sonnet are called through Bedrock and their outputs vary between invocations, so their rows shift too.

Expect scores within roughly ±0.05 of the values above. Judge the lab by whether the *ordering* holds, not by matching exact numbers.

### What to look for instead

These conclusions should hold in your run:

1. **SFT + RLVR ranks first**, with plain SFT close behind. The RLVR increment over SFT is genuinely small — if the two swap places in your table, that is within noise on a 37-sample split and not a finding.
2. **Both fine-tuned models clearly beat RLVR-only and the base model**, confirming Lab 3's ablation from a second angle.
3. **The fine-tuned 3B beats both frontier models by a wide margin** on Exact Match and Result F1. This gap is large enough that it should not invert.
4. **Exec Success is high for everyone.** Every model can write syntactically valid SQL — the separation comes from Exact Match and Result F1, which measure whether the query returns the *right answer* against your schema.

---

## Key finding

A 3B parameter model fine-tuned on ~200 examples with SFT+RLVR **outperforms frontier models** that have never seen your schema. Domain specialization compensates for model scale.

Note what this does and does not claim. Claude Sonnet is not a worse SQL model than Llama 3.2 3B — it is a far better one in general. It simply has never seen your tables, columns, or join conventions, and no amount of scale substitutes for that. The comparison is about schema knowledge, not raw capability.

## Cleanup

**At an AWS event, there is nothing to clean up.** The account was provisioned for this workshop, you are not charged for anything in it, and it is reclaimed automatically once the event ends. You can close the browser.

If you are adapting this workshop into **your own AWS account**, you are responsible for everything it provisions. The table below lists every resource, ordered by **what costs you money while it sits idle** — work down from the top.

Note that three of these were created by the notebooks rather than by CloudFormation, so they survive a stack deletion and must be removed separately.

| Resource | Created by | Cost impact | How to remove |
|---|---|---|---|
| Aurora PostgreSQL Serverless v2 cluster | CloudFormation | **Ongoing — the largest.** Billed per ACU-hour continuously. `MinACU` is `0.5`, so the cluster never pauses and bills even when nothing queries it. Storage is charged separately. | Deleted by the stack |
| MLflow tracking server (`workshop-mlflow`) | `00-setup.ipynb` | **Ongoing.** Billed per hour for as long as it exists. There is no "stop" — the only way to stop charges is to delete it. | SageMaker AI console → MLflow → delete the tracking server |
| JupyterLab space (`ml.t3.xlarge`) | Getting Started | **Ongoing while running.** Instance charges stop when you stop the space, but its storage volume keeps billing until the space is deleted. | SageMaker Studio → stop the space, then delete it |
| S3 buckets (`slm-weights-*`) | CloudFormation | **Ongoing, size-dependent.** Storage only, but model checkpoints from three training runs are the bulk of it — gigabytes, not megabytes. | Deleted by the stack, which now empties them first |
| Secrets Manager secret | CloudFormation | **Ongoing but small** — a flat per-secret monthly charge. | Deleted by the stack (see the note below) |
| SageMaker AI Domain | CloudFormation | **Small ongoing storage cost** for the file system backing the domain. | Deleted by the stack |
| VPC, subnets, security group | CloudFormation | **Free.** There is no NAT Gateway in this template, which is the usual source of unexpected VPC charges. | Deleted by the stack |
| Evaluator Lambda (`workshop_evaluator`) | `02-supervised-fine-tuning.ipynb` | **Free at rest** — you pay per invocation, and nothing invokes it once the labs finish. | Lambda console → delete the function |
| Completed training and evaluation jobs | Labs 2 and 3 | **Free.** Billing stops the moment a job reaches a terminal state. Nothing to delete. | Nothing to do |
| Model packages, registered datasets | Labs 1, 2 and 3 | **Free to retain** as registry entries. But the artifacts they point at live in the S3 buckets above, which is where the actual cost is. | Nothing to do — remove the buckets instead |

**Priority if you only do one thing:** delete the Aurora cluster and the MLflow tracking server. Those two bill by the hour regardless of whether you touch them, and between them they account for nearly all of the idle cost.

Delete the notebook-created resources first, then delete the `sm-stack` CloudFormation stack for everything else.
